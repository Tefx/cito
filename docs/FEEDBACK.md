# Cito Dogfooding & Field Feedback Ledger

This document collects real-world usability, reliability, and workflow observations from active multi-host and multi-session Cito dogfooding. Items recorded here are periodically reviewed and triaged into architectural decisions or implementation phases.

## How to Record or Submit Feedback

- **Via Cito Signaling**: Any active agent session can send feedback directly to the Cito repository's architect or orchestrator session via `cito_send` (discoverable through `cito_find` with `repo` or `query: "cito"`).
- **Direct Documentation Update**: Sessions working in this repository should append newly received field feedback to the **Open Feedback Items** table below using English and vendor-neutral examples (`personal`, `work`, `alice`, `bob`, `acme/service`).

| **FB-03** | 2026-11-23 | Rebuilding `/Applications/Cito.app` (`cito setup --build-app /Applications`) on a Mac running `host_hub` (`0.0.0.0:4291`) without bumping SemVer | Bundle Replacement & macOS Application Firewall (`setup.rs`, `plugins.rs`) | When `cito setup --build-app /Applications` replaces `/Applications/Cito.app` on disk without a SemVer bump (`0.22.0` -> `0.22.0`), `reconcile()` calls `ensure_daemon`, which sees `daemon_version_satisfies(Some("0.22.0"), "0.22.0") == true` and leaves the old daemon PID running from its unlinked executable inode. Because the running process's in-memory code signature no longer matches the replaced `/Applications/Cito.app` bundle on disk, macOS Application Firewall (`socketfilterfw`) immediately resets (`RST`) all non-loopback (`en0` LAN / `utun` Tailscale) inbound TCP connections to `:4291` after the 3-way handshake while `127.0.0.1:4291` (`lo0`) continues to return `200 OK`. | In `setup.rs` (`build_app` branch), unconditionally stop any running daemon for `state_dir` (`stop_daemon`) before calling `ensure_daemon(&config)` so rebuilding `/Applications/Cito.app` always restarts the daemon from the newly signed on-disk bundle inode. | `OPEN (Live mitigated)` |
| **FB-04** | 2026-11-23 | Peer TCP reset / empty EOF during HTTP request (`crates/cito-native/src/core/plugins.rs:1018` & `transport.rs`) | Error Diagnostics (`plugins.rs`, `transport.rs`) | When a remote HTTP endpoint closes or resets the connection before sending any response bytes (`0` bytes read on `status_line` in `read_http_response`), `line()` hits `!bytes.ends_with(b"\n")` and returns the misleading message `"Truncated or oversized HTTP headers"` wrapped with a legacy `"NATS_UNAVAILABLE: "` prefix. | Distinguish `bytes.is_empty()` on the initial status line in `read_http_response` (`"Connection closed by peer before HTTP response"`), and review legacy `NATS_UNAVAILABLE:` diagnostic prefixes on pure HTTP/SSE transport errors. | `OPEN` |
| **FB-05** | 2026-11-23 | Same-host session discovery and signaling when the default remote Hub is temporarily unreachable | Multi-Hub & Local Fallback Resilience (`setup.rs`, `daemon/mcp.rs`) | If the built-in `"local"` Hub (`url: "local://"`) is disabled on a client Mac (`"local": {"enabled": false}`) and the default remote Hub is temporarily unreachable over LAN/Tailscale, same-host sessions on that Mac cannot discover or message each other even though they share the same local `cito-native daemon` and `state.sqlite`. | Keep the built-in `"local"` Hub enabled alongside remote Hubs on client Macs (where `host_hub` is not enabled), or allow same-host fallback discovery/routing via `"local"` when a remote Hub is unreachable. | `OPEN (Live mitigated)` |
| **FB-06** | 2026-11-23 | User visual inspection of inbound wake cards vs. outbound `cito/*` tool calls in Pi TUI | Unified Action & Card Visual Style (`plugins/pi/cito-bridge.ts`) | In Pi TUI, inbound Cito messages render through `registerMessageRenderer("cito-notification")` (purple `customMessageBg` card with `Cito · ...` header and `│ ` left border), whereas Cito actions (`cito/cito_inbox`, `cito/cito_send`, `cito/cito_find`, `cito/cito_status`, `cito/cito_listen`) render through Pi's generic MCP tool fallback (green box with `cito/<tool> key=val...` and raw JSON receipts like `{"expires_at":...,"signal_id":...}`). In addition, agents waking from a `cito-notification` card sometimes redundantly call `cito_inbox ack_all=true` (`acknowledged_count: 0`) even though the wake card was already auto-acknowledged. | Unify Cito's visual presentation in `plugins/pi/cito-bridge.ts` (for example, by providing custom `renderCall` / `renderResult` formatting for Cito tool invocations—such as clean human-readable headers like `Cito ↗ <to>` and compact status summaries instead of raw JSON—aligned with the `cito-notification` card typography/padding), and clarify in wake-card/tool descriptions that delivered wake cards are already acknowledged so agents do not make redundant `cito_inbox` calls. | `OPEN` |

| **FB-R1** | 2026-11-22 | Multi-host setup (`host_hub` enabled on host Mac + CLI `cito setup --hub` pointing to own shared Hub URL) | Hub Slot Authority & UI Stability (`DSE-1`) | Adding a client Hub profile on the same Mac that hosts that shared Hub (`host_hub`) caused `"local"` and the self-pointing HTTP slot to overwrite each other's `binding_generation` and `owner_token` every ~500ms (`ACTIVE <-> FENCED_INACTIVE`), making the menu bar UI flicker between `listeners` and `available`. | Closed in **Phase `v58` (`ec42cc6`, `DSE-1`)**: unified `is_own_host_hub_url` and `validate_hub_endpoints` across all write admission boundaries (`paste_hub_invite`, `setup_save_hub`, `set_host_hub`, CLI `cito setup`) and skip self-loop/duplicate-endpoint slots in `reload_slots`. | `RESOLVED (v58)` |
| **FB-R2** | 2026-11-22 | Long-running tool calls in Pi sessions under `autoListen` | Harness Probe Equivalence (`DSE-2`) | `plugins/pi/native.rs` used `socket_response_or_cached` in `discover_sessions` but bypassed it in `probe`.
