Subprocess Plugin Authoring Guide

Cito's Rust core launches concrete agent and channel integrations as subprocesses. A declarative plugin.json supplies the command, UI metadata, and configuration fields. Implement the protocol in any language; no in-process adapter or TypeScript SDK is required. Write one JSON object per line to stdout, read requests from stdin, and send diagnostic logs to stderr.

1. Plugin Discovery & Manifests

Packaged plugins live in plugins/<id>/, including Contents/Resources/plugins inside Cito.app. CITO_BUILTIN_PLUGINS_DIR selects a packaged plugin directory. The desktop host also reads ${CITO_STATE_DIR}/plugins/<id>/ (default ~/.cito/plugins/<id>/) and colon-separated roots in CITO_PLUGIN_PATH. Standalone cito hub reads channel plugins from its bundled roots, CITO_PLUGIN_DIR, and <data-dir>/plugins, with later roots overriding earlier manifests of the same ID.

  • id: ^[a-z0-9][a-z0-9_-]{0,31}$; external plugin directory names must match the ID. displayName must be nonempty.
  • kind: agent-harness or human-channel. The aliases agent and human normalize to those names.
  • tier: stable or experimental (default stable).
  • command: a nonempty array of executable and arguments. Executables starting with ./ or ../ resolve relative to the plugin directory. Provide the executable and set its executable permission.
  • sfSymbol, tint, and cliFlag control presentation and CLI enrollment. scope defaults to hub; fields and pairing declare configuration and account binding.

External plugins that omit command can use an index.js entrypoint, or index.ts with Node's --experimental-strip-types. These entrypoints still speak the subprocess protocol and require a compatible Node installation. An explicit command avoids that runtime dependency for native plugins.

2. Contract 1: agent-harness

Create ~/.cito/plugins/sample-agent/plugin.json and install your executable at bin/cito-plugin-sample-agent:

{
  "id": "sample-agent",
  "kind": "agent-harness",
  "displayName": "Sample Agent",
  "tier": "experimental",
  "sfSymbol": "terminal",
  "tint": "purple",
  "cliFlag": true,
  "command": ["./bin/cito-plugin-sample-agent"]
}

For a one-shot operation, the host writes a JSON request followed by a newline and closes stdin. The subprocess returns one JSON response line and exits. Requests include state_dir and env; setup requests also include plugin_dir. The host enforces a 10-second deadline and kills timed-out children. Nonzero exits or invalid JSON produce PLUGIN_EXEC_FAILED.

OperationRequest / response contract
setup_inspectInspect installed configuration. Return {"ok":true,"installed":true,"configured":true,"paths":["..."]}.
setup_applyHonor dry_run and force. Return actions with target, path, status (created, updated, unchanged, or conflict), backupPath, and detail.
setup_removeHonor dry_run; remove only owned configuration and return actions.
discover_sessionsReturn {"ok":true,"sessions":[...]}. Each session carries harness, session_id, cwd, repo, branch, title, endpoint_pid, and updated_at_ms.
resolve_callerResolve meta, headers, cwd, http_client_pid, http_transport, require_open, cli_cmd, and explicit_session_id. Return {"ok":true,"caller":{...}} with the session fields, or {"ok":false,"error_code":"BINDING_REQUIRED","message":"..."}.
probeCheck session_id, cwd, and endpoint_pid. Return ok, status (alive, switched, closed_definitive, or transient_error), current_session_id, and reason.
update_badgeSet or clear badge for the session and endpoint. Return {"ok":true}.
wakeDeliver the rendered text and signals for batch_id; honor the wake flag. Return outcome: delivered, delivered_unconfirmed, session_switched, or driver_unavailable, plus ok and reason.
 
{"op":"wake","session_id":"session-1","cwd":"/Users/alice/repo","endpoint_pid":1234,"batch_id":"b_1","wake":true,"text":"Review needed","signals":[{"signal_id":"s_1","from_listener_id":"bob-sample-agent-session-2","from_user":"bob","from_harness":"sample-agent","from_title":"Review","message":"Please review","created_at":"2026-09-01T00:00:00Z","in_reply_to":null}],"state_dir":"/Users/alice/.cito","env":{}}
{"ok":true,"outcome":"delivered","reason":null}

Multi-effect wake handlers support checkpoint_only, queue_written, and queue_confirmed. Return the insertion checkpoint with queue_written: true, its actual queue_confirmed value, and continue_wake: true before a separate wake effect. The host persists the checkpoint and revalidates unreadness, binding, generation, owner, and Hub claim. On the next request, skip insertion when queue_written is true; an unknown insertion (queue_confirmed: false) must never be resubmitted. Omitting continue_wake completes the operation. Single-effect plugins may ignore checkpoint_only. A process death before the checkpoint response retains an at-least-once delivery limitation.

Optional streaming sidecar

Set channelEnv to the environment variable that enables your streaming integration in cito mcp-stdio. The host sends {"op":"stdio_sidecar","endpoint_pid":1234,"cwd":"...","state_dir":"...","env":{}} and keeps stdin open. Emit {"op":"ready","capabilities_patch":{...}} first, then JSON-RPC notification frames on stdout. Monitor stdin EOF and exit when the parent closes it.

3. Contract 2: human-channel

Hub-scoped human channels run as persistent subprocesses owned by HubEngine. The Hub starts a process when required Hub configuration is present or an on-demand pairing/test RPC arrives. It sends shutdown and terminates the process when all bindings are disabled and Hub configuration is cleared. Monitor stdin on a dedicated reader and exit within 100 ms of EOF to avoid orphan processes. The local desktop UI uses the separate UI IPC contract with scope: "user". 

{
  "id": "sample-chat",
  "kind": "human-channel",
  "displayName": "Sample Chat",
  "tier": "experimental",
  "scope": "hub",
  "sfSymbol": "bubble.left.fill",
  "tint": "blue",
  "command": ["./bin/cito-plugin-sample-chat"],
  "fields": [
    { "key": "apiToken", "scope": "hub", "label": "API Token", "type": "secret", "required": true },
    { "key": "recipientId", "scope": "user", "label": "Recipient ID", "type": "string", "required": true }
  ],
  "pairing": { "supported": true, "actionLabel": "Pair Account…" }
}

Hub → plugin (stdin NDJSON)

  • configure: hub_config, bindings (each with principal_id, user, config), and persisted cursor.
  • deliver: delivery_id, principal_id, user, recipient config, and signal (ID, sender, recipient, kind, summary, message, and creation time).
  • on_acked: principal_id, signal_ids, acked_at_ms, external_msg_ids, and user_config, for synchronizing external read state.
  • format_pair / test: correlated RPC requests with req_id and hub_config. Pair formatting includes code; testing includes user and user_config.
  • pair_ack: code, ok, owner_user, and error. reply_ack: update_id, ok, target_display, and error.
  • {"op":"shutdown"}: release external connections and exit.
{"op":"configure","hub_config":{"apiToken":"example-token"},"bindings":[{"principal_id":"none#alice","user":"alice","config":{"recipientId":"room-1"}}],"cursor":"100"}
{"op":"deliver","delivery_id":"d_1","principal_id":"none#alice","user":"alice","config":{"recipientId":"room-1"},"signal":{"signal_id":"s_1","from":{"listener_id":"bob-sample-agent-session-2","canonical_id":"c_sender","harness":"sample-agent","title":"Review"},"to":{"listener_id":"alice-human-default"},"kind":"NeedInput","summary":"Review needed","message":"Please review","created_at_ms":1700000000000}}

Plugin → Hub (stdout NDJSON)

  • delivered: report delivery_id, ok, external_msg_id, all external_msg_ids, and error after the external delivery result is known.
  • pair_redeem: provide code, external_chat_id, external_user_id, is_private_chat, display_label, and user_config_patch.
  • inbound_reply: provide update_id, external_chat_id, external_user_id, reply_to_external_msg_id, and text. The Hub resolves the reply target and routes a regular signal.
  • cursor_save: persist the channel's external update cursor.
  • rpc_result: echo req_id, ok, and error; pair formatting returns instruction and optionally bot_username, while testing returns detail.
{"op":"delivered","delivery_id":"d_1","ok":true,"external_msg_id":"102","external_msg_ids":["101","102"],"error":null}
{"op":"inbound_reply","update_id":"u_99","external_chat_id":"room-1","external_user_id":"user-1","reply_to_external_msg_id":"102","text":"Ship it"}
{"op":"cursor_save","cursor":"101"}

Correlate delivery and RPC responses by their IDs. The Hub persists delivery mappings for reply resolution and read synchronization. If a subprocess exits with pending RPCs, callers receive {"ok":false,"error":"Plugin subprocess exited"}.

4. Configuration & Pairing

The UI renders manifest fields automatically: fields[].scope: "hub" holds shared credentials, while fields[].scope: "user" holds each user's recipient binding. This field scope is independent of the plugin's process scope. With pairing.supported: true, the Hub generates a 10-character Base32 pairing token displayed with the cito- prefix. Implement this exchange: 

{"op":"format_pair","req_id":"r_1","code":"cito-a1b2c3d4e5","hub_config":{"apiToken":"example-token"}}
{"op":"rpc_result","req_id":"r_1","ok":true,"instruction":"Send /start cito-a1b2c3d4e5 in a private chat","error":null}
{"op":"pair_redeem","code":"cito-a1b2c3d4e5","external_chat_id":"room-1","external_user_id":"user-1","is_private_chat":true,"display_label":"alice","user_config_patch":{"recipientId":"room-1"}}
{"op":"pair_ack","code":"cito-a1b2c3d4e5","ok":true,"owner_user":"alice","error":null}

The Hub validates the pairing code and ownership before accepting the binding. Human replies and agent messages use the same Hub signaling path; plugins must not bypass it with external window jumps.
