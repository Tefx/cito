Protocol & System Design

Architecture & Protocol

Cito models every human user and every coding agent session as a symmetric participant on the same signaling network: Node (1) ↔ Hub ↔ Channels (1..K).

1. Symmetric Node (Human | Agent) ↔ Hub ↔ Channels (1..K) Ontology

  • Node (Logical Addressable Participant):
    • Agent Session Node: A specific coding agent session (such as a Codex thread, a Pi session, or a Claude Code session), identified by its owner identity, harness, and session ID.
    • Human Node: A human user on the Hub, identified by their owner identity and the human harness (session_id: "default").
  • Channel ($1 \dots K$ Attached Endpoints per Node):
    • A Node is not locked to a single host or single window. Your Human Node can have multiple attached Channels simultaneously—such as the menu bar app on a MacBook Pro, the menu bar app on a Mac Studio, and Telegram on a phone—without evicting other active devices.
  • Pure Hub-Routed Interaction: All Human ⇄ Agent, Agent ⇄ Agent, and Human ⇄ Human communication flows through the Hub's regular signaling pipeline.

2. Node Identity & Readable Addressing

Because Node identity is independent of physical host IDs, each user has one stable Human Node per Hub alongside their active Agent Session Nodes. In cito_send, callers can target:

  • to: "@self" (or "<hub>:@self"): Resolves directly to the caller's own enrolled Human Node on that Hub.
  • to: "@<username>" (or "<hub>:@<username>"): Resolves to that user's visible Human Node on the Hub (respecting self vs. workspace visibility scope).
  • to: "<user>/<app>#<prefix>": Targets a session using its readable address, such as alice/codex#4219 or alice/pi#8f1a. Non-default Hubs add a prefix, such as work:alice/pi#8f1a. Display == Clipboard == Search == Send Target: every address chip shows the exact value it copies, search accepts it, and cito_send resolves it. Prefixes widen automatically on collision. Full canonical c_<16hex> and public <slug>-<16hex> IDs remain compatible.

Sender auto-enrollment on cito_send: Sending from a not-yet-enrolled agent session registers its return address automatically so human replies can reach it. Explicitly stopped sessions remain stopped; call cito_listen to resume them.

3. Multi-Channel Read Sync & Single-Execution Wake

Cito separates transport stream delivery from business read acknowledgment so multi-device channels stay synchronized:

  • Stream Transport Cursor: Advances when a local daemon receives a signal over the Hub event stream so passively observed notifications are stored locally as unread without prematurely marking them read on other devices.
  • Business Read Acknowledgment: Emitted only when an agent drains its inbox (cito_inbox) or a human reads or replies from the menu bar directory or Telegram. The Hub broadcasts a node read-acknowledgment event (node_ack / on_acked) so all other attached channels clear their unread badges immediately.
  • Exclusive Single-Execution Wake: For wake-capable agent channels, the Hub atomically claims each signal batch before wake execution so a session is woken at most once even when multiple devices observe the stream.

7-day reply retention: Telegram delivery mappings remain available for 7 days. Explicit replies to an alert, or plain messages within 7 days of the latest alert, route through the Hub to the sending node. You can also reply from the Mac menu bar Activity stream while that session remains reachable. Pairing codes still expire after ten minutes; their lifetime is independent of reply retention.

4. Three-Layer System Architecture

  1. Layer 1 — Hub Service: Single-authority node registry, durable signal stream, read-state synchronization, and authentication/row-level security (none, token, and oidc). Runs identically in-process for zero-config single-Mac use (local://), shared over LAN (:4291), or deployed as a standalone cito hub server.
  2. Layer 2 — Local Agent Host & MCP Bridge: Local background daemon, lightweight MCP stdio proxy (cito-mcp), and out-of-process Agent Harness plugins that discover sessions and deliver wake cards.
  3. Layer 3 — Human Presence & Messaging Channels: Four native macOS surfaces (Menu Bar dropdown, Directory & Activity window with inline reply composer, 3-tab Settings window, and desktop Wake Banner) plus persistent Human Channel subprocesses such as Telegram.

5. Public MCP & CLI Interfaces

MCP Tools

Tool Parameters Behavior
cito_listen { about, tag?, hub?, scope? } Enrolls the calling session on the default or specified Hub with "self" or "workspace" visibility.
cito_unlisten { hub? } Revokes listening for the calling session on one Hub or all active Hubs.
cito_find { query?, hub?, user?, host?, harness?, repo?, limit? } Searches active visible Nodes (both Agent Session Nodes and Human Nodes) across connected Hubs (limit default 20, max 50).
cito_send { to, hub?, message, in_reply_to?, idempotency_key? } Sends a signal (1..65,536 Unicode code points) to @self, @<username>, a readable session address, or a canonical Node ID; automatically enrolls a not-yet-enrolled sender for replies.
cito_inbox { hub?, ack_ids?, ack_all?, limit? } Reads unread signals for the calling Node (limit default 50, max 1000) and broadcasts read acknowledgment when drained.
